# Волга-IT 2026. Финал. «Искусственный интеллект и анализ данных»

## Настроение в домовых чатах

### 1. Введение

У каждого многоквартирного дома теперь есть чат в мессенджере. Жители обсуждают в нём отключения воды,
работу управляющей компании (УК), шум, парковку и соседских собак. Туда же приходят рассылки «Госуслуги Дом»,
объявления УК и реклама.

Органам жилищного надзора и самим УК важно видеть, **где и когда растёт напряжение**: в каком доме жители
третью неделю недовольны, где вчера вспыхнул конфликт, где после ремонта стало спокойнее. Читать тысячи
чатов вручную невозможно.

**Задача финала:** разработать систему, которая по выгрузке сообщений домовых чатов
1. определяет для каждого сообщения, служебное ли оно, его тональность и есть ли в нём агрессия;
2. агрегирует результаты по каждому чату и по дням;
3. показывает динамику настроения во времени в понятном отчёте.

Интеграция с API мессенджеров не требуется: на вход подаётся CSV-файл.

### 2. Данные

Реальные сообщения домовых чатов Ленинградской области, июнь–июль 2026 года. Данные **обезличены**:
имена, телефоны, адреса, номера квартир и автомобилей, e-mail и ссылки заменены маркерами
`[имя] [телефон] [адрес] [квартира] [грз] [email] [ссылка] [ник] [номер]`. Идентификаторы чатов и
пользователей заменены псевдонимами и согласованы между всеми файлами: один и тот же `user_id` — это один и
тот же отправитель. Время — московское.

| файл | что внутри |
| --- | --- |
| `data/train.csv` | ~4 000 размеченных сообщений из ~1 300 разных чатов (случайная выборка, без контекста чата) |
| `data/dev_messages.csv` + `data/dev_labels.csv` | 4 чата целиком, ~1 100 сообщений с разметкой. **Формат точно как у скрытого теста** |
| `data/unlabeled.csv` | ~20 000 неразмеченных сообщений из 105 чатов, полные потоки |
| `labeling_guide.md` | инструкция, по которой размечены данные. **Обязательна к прочтению** |
| `chatmood_metrics.py` | эталонный расчёт агрегатов (раздел 4); можно импортировать |
| `evaluate.py` | автоматическая часть оценки — тот же код, что у жюри |

Формат входного CSV (разделитель `;`, UTF-8, первая строка — заголовок):

```
message_id;chat_id;timestamp;user_id;text
m110547;c1694;2026-06-15 09:12:44;u04811;Опять нет горячей воды, сколько можно?!
```

В `train.csv` и `dev_labels.csv` добавлены метки:

- `is_service` — 0/1: рассылка, официальное объявление, реклама (1) или реплика жителя (0);
- `sentiment` — `negative` / `neutral` / `positive`: тональность автора;
- `aggression` — 0/1: оскорбления, грубость, переход на личности.

В `dev_labels.csv` есть ещё `tags` — теги сложных случаев: `sarcasm`, `obscene`, `typos`, `jargon`, `emoji`,
`mixed`, `context`. Правила разметки и спорные случаи описаны в `labeling_guide.md`. Для служебных
сообщений по соглашению `sentiment = neutral`, `aggression = 0`.

Разрешено использовать любые открытые датасеты и предобученные модели (RuSentiment, RuSentiTweet,
модели с HuggingFace и т. п.). Также можно доразмечать данные самостоятельно, в том числе с помощью
LLM (с обязательной проверкой качества, п. 4.3 регламента). Источники указываются в README.

### 3. Что должно делать решение

Решение запускается одной командой на CSV в формате входа и пишет в выходной каталог:

```
python predict.py --input <messages.csv> --out <каталог>
```

(имя скрипта и аргументы могут быть другими, но команда должна быть одна и указана в README)

**3.1. `messages_pred.csv`** — по строке на каждое сообщение входа:

```
message_id;is_service;sentiment;aggression
m110547;0;negative;0
```

Можно добавлять колонки с вероятностями (`p_negative` и т. п.), они не оцениваются, но полезны для отчёта.

**3.2. `chat_daily.csv`** — по строке на каждую пару (чат, день), в которой было хотя бы одно сообщение:

```
chat_id;date;n_messages;n_resident;mood_index;negative_share;aggression_share
c1694;2026-06-15;12;10;-0.3;0.4;0.1
```

**3.3. `chat_summary.csv`** — по строке на чат:

```
chat_id;n_resident;mood_index;negative_share;aggression_share;trend;peak_days
c1694;308;-0.37;0.41;0.05;worsening;2026-07-01|2026-07-04|2026-07-08
```

**3.4. Отчёт** (`report.html`, ноутбук или PDF) с аналитикой по чатам: динамика во времени, сравнение
чатов, дни-пики и что в них происходило, всё, что поможет инспектору быстро понять ситуацию.

### 4. Как считаются агрегаты

Все доли и индексы считаются **только по сообщениям жителей** (`is_service = 0`). Дата — по московскому
времени из `timestamp`.

- `n_messages` — все сообщения чата за день; `n_resident` — сообщения жителей.
- `mood_index = (n_positive − n_negative) / n_resident`, от −1 до +1.
- `negative_share = n_negative / n_resident`; `aggression_share = n_aggression / n_resident`.
- Если `n_resident = 0`, доли и индекс пустые.
- `trend` (за весь период чата):
  1. Берутся ISO-недели (пн–вс), в которых `n_resident ≥ 5`.
  2. Если таких недель меньше трёх, `stable`.
  3. Иначе строится взвешенная по `n_resident` линейная регрессия недельного `mood_index` на номер недели.
     Наклон > 0,05 → `improving`, < −0,05 → `worsening`, иначе `stable`.
- `peak_days` — до трёх дней с `n_resident ≥ 5` с наибольшим `n_negative + 2·n_aggression` (только если он
  больше нуля), через `|`, по возрастанию даты.

Эталонная реализация — `chatmood_metrics.py`. Жюри считает эталонные агрегаты этим же кодом по эталонной
разметке и сравнивает с вашими файлами. Поэтому качество агрегатов зависит и от классификации, и от того,
насколько точно вы отделяете служебные сообщения.

Сверх обязательных полей приветствуется собственная аналитика в отчёте: сглаживание, доверительные
интервалы для дней с малым числом сообщений, темы конфликтов, активность по часам, сравнение чатов.

### 5. Требования

1. **Офлайн-инференс.** Во время работы `predict.py` нельзя обращаться к внешним API (LLM-сервисы, облачные
   модели). Все веса и словари — локально, вместе с решением. Внешние LLM можно использовать на этапе
   разработки: для разметки, генерации данных, написания кода.
2. **Ресурсы.** Решение должно работать на ПК жюри: Intel Core i5-7600, GeForce GTX 1050 Ti 4 ГБ, 16 ГБ ОЗУ,
   набор библиотек как на рабочих местах финала. Время замеряется на скрытом тесте (~4 500 сообщений).
   Ориентир для максимального балла — до 10 секунд на 1000 сообщений.
3. **Воспроизводимость.** Есть скрипт обучения, фиксированные random seed, README с командами установки,
   обучения и запуска. Обученные модели сдаются вместе с кодом (облако, если файлы большие).

5. отчёт с аналитикой (п. 3.4) по dev.

### 7. Как оценивается

Жюри запускает `predict.py` на **скрытом тестовом наборе**: ~22 других чата целиком, около 4 500 сообщений,
с большей долей конфликтов и сложных случаев. Автоматические метрики считаются тем же кодом, что в
`evaluate.py`.

| критерий регламента (п. 5.2) | баллы | как оценивается |
| --- | --- | --- |
| 1. Качество классификации сообщений | 20 | авто: 0,6·macro-F1 тональности (по сообщениям жителей) + 0,2·F1 агрессии + 0,2·F1 служебных |
| 2. Качество агрегации по чату | 20 | авто 14: ошибка дневного индекса, корреляция дневной доли негатива, ранжирование чатов, тренд, дни-пики; эксперт 6: методика агрегации |
| 3. Специфика русского языка и доменной лексики | 15 | авто 8: macro-F1 на сложных подвыборках (сарказм, мат, опечатки, жаргон, эмодзи…); эксперт 7 |
| 4. Предобработка и обоснование архитектуры | 10 | эксперт |
| 5. Интерпретируемость, отчёты, визуализации | 10 | эксперт |
| 6. Быстродействие и ресурсоёмкость | 5 | замер на ПК жюри |
| 7. Воспроизводимость, документация | 5 | эксперт + запуск по README |

Если решение не запускается по инструкции, автоматические критерии оцениваются в 0.
